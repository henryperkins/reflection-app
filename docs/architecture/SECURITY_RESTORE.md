# Restore invariants and the independent recovery ledger

This file is authoritative for cross-store security ordering. It qualifies the simpler D1-only state descriptions: no database restore may revive erased data, removed authentication factors, spent recovery codes, old model permission, or scheduled inference. R2 holds **encrypted minimal erasure targets, erasure progress/completions and encrypted identity recovery checkpoints**. It does not hold journals, prompts, account DEKs, raw recovery codes, sessions or exports.

## Ledger object contracts

The authoritative shapes are ErasureTarget, RecoveryCiphertext, ErasureIntent, ErasurePass, ErasureCompletion and IdentityCheckpoint in DOMAIN_CONTRACTS.ts. Ledger objects are at most16KiB, except identity checkpoints at most64KiB. The notation here defines their encoding, storage and ordering.

`ErasureIntent` is conditional-created at `erasures/v1/<jobId>/intent.json`. It includes scope, subjectHmac, targetHmac, hmacKeyId, requestedAt, an independently encrypted `target`, receiptTokenHmac (null for internal operations without a user receipt), and operationMac. The target contains only these canonical identities:

| Scope | Exact decrypted target and resolution |
|---|---|
| account | `{scope,subjectId}` → the owned account and every registered owned family. |
| session | `{scope,subjectId,sessionId}` → the exact owned session, its children and all downstream copies. |
| reflection_revision | `{scope,subjectId,reflectionId,revision}` → that immutable revision and copies; never substitute the current revision. Other authored revisions survive unless independently targeted. |
| context_copy | `{scope,subjectId,source}` where source is `{kind:'edition',editionId}` or `{kind:'reflection_revision',reflectionId,revision}` → copies of that exact source; keep the original unless a session/revision erasure or content-withdrawal policy also removes it. |

Encode UTF-8 JCS, with canonical lowercase UUIDs and integer revisions, no inferred IDs or names. `subjectHmac=HMAC-SHA256(K[hmacKeyId],JCS(['erasure-subject.v1',env,subjectId]))`; targetHmac uses `['erasure-target.v1',env,target]`. The HMAC key is an environment-level recovery key, independent of account keys. Encrypt JCS(target) with AES-256-GCM under `RECOVERY_KEK[target.keyId]`, random12-byte nonce, AAD `JCS([env,'erasure-target.v1',jobId,scope,subjectHmac,targetHmac,hmacKeyId,requestedAt,target.keyId])`. `deletion_jobs.target_enc` holds the same envelope while pending; the R2 copy survives its removal or rollback. Authenticate every ledger object with its own hmacKeyId: operationMac is HMAC of `JCS([env,objectKind,objectWithoutOperationMac])`, using distinct kinds `erasure-intent.v1`, `erasure-pass.v1`, `erasure-completion.v1`. SHA references cover the exact canonical stored bytes including MAC. Receipt HMAC uses `['erasure-receipt.v1',env,jobId,rawToken]`; it permits rebuilding status verification without retaining a raw capability.

Each erasure execution has a positive integer revision. Before touching restored data, conditional-create `erasures/v1/<jobId>/passes/<revision>/start.json` containing ErasurePass: intentSha256, startedAt, and previousCompletionSha256 (null only for revision1). After verified active-store erasure, create `passes/<revision>/complete.json` containing ErasureCompletion with the same job/revision/intent and passSha256. Decimal revisions have no leading zeros and are ordered numerically, never by list order. A retry reuses the stored start object and exact completion bytes. No overwrites; differing bytes at an existing immutable key are an incident. Serialize passes per job; a new pass requires the preceding completion. A crash with a start but no completion leaves the job pending indefinitely, even if older completions exist.

The authoritative status is the highest contiguous authenticated pass chain, with every referenced digest and key verified. Any gap, unexpected object, missing key or invalid MAC blocks replay/cleanup. A later incomplete pass means pending and `backupExpiresBy:null`. For a completed pass, `backupExpiresBy=max(previous backupExpiresBy,erasedAt+30days)` and `purgeAfter=max(previous purgeAfter,erasedAt+45days,backupExpiresBy+15days)`; initial previous values are absent. Take the maximum validated deadlines across the whole chain; never shorten them. Every offline restore starts a new pass (or resumes an incomplete one) and records a new completion after verification, even when its target is already absent. Thus another restored copy extends protection from its new erasure boundary. Date corrections also append a pass/completion; they never rewrite an object.

Replay lists all pages (at most100 objects/page), validates one job chain at a time, decrypts its target using the named retained key, and verifies scope and both HMACs against the plaintext. No D1 deletion job or keyed-ID brute-force lookup is needed. Resolve by subject plus exact target IDs against the fixed lifecycle registry; enumerate downstream reference/copy families in batches of at most100 rows, including encrypted provenance and import previews. Do not stop at a missing source row: surviving copies still require inspection. Maintain a resumable D1 cursor only as an optimization; if lost, restart the idempotent scan. Detach erased import aliases into tombstones before deleting referenced rows. Missing required content keys or unresolved ownership prevents completion. Reconstruct a minimal job/receipt projection from the intent and chain if D1 lost it; that projection never replaces R2 authority. Mark complete only after every family and copy check succeeds.

Cleanup pauses and drains before offline restore; it cannot run concurrently with replay or a deadline correction. Purge an entire job prefix only after the latest pass is complete, the maximum purgeAfter has elapsed, and no supported backup can contain the target. Interrupted cleanup must not cause unverified data to be served. Retain every named HMAC and recovery encryption key until all referencing intents, passes, completions and checkpoints are purged, including offline recovery copies; pending references retain keys indefinitely. Rotation uses new IDs for new objects and retains old keys for verification/decryption. Never rewrite an immutable intent to retire a key. Lost keys keep restore offline.

`IdentityCheckpointV1`: encrypted operational envelope with immutable payload revision/auth epoch. Decrypted body `{v:1,operationId:UUID,subjectId:UUID,epoch:positiveInt,createdAt:UTC,recoveryHandleHash:hex64,recoveryAcknowledgedAt:UTC|null,credentials:[{id:base64url,publicKey:base64url,signCount:nonnegativeInt,backedUp:boolean,transports:string[],createdAt:UTC}],recoveryCodes:[{codeHash:hex64,usedAt:UTC|null,createdAt:UTC}]}`. Max10 credentials/10 codes/64KiB. Only hash verifiers, never raw handle/code/session/CSRF values. Key `identity/v1/<subjectHmac>/<epoch>-<operationId>.enc`; encrypt under separate RECOVERY_KEK with AAD `[env,'identity-checkpoint',subjectHmac,epoch,operationId,1]`. Latest checkpoint remains for account lifetime; superseded checkpoints retained45days then removed. Account-erasure intent overrides all identity checkpoints; erase all its checkpoints after active account erasure is confirmed (keep minimal erasure intent through backup expiry). Ledger secrets remain offline-backed-up separately from D1. No public bucket/CDN URLs.

Live authentication remains authoritative in D1. Checkpoints exist solely for crash/restore replay and contain a complete state to avoid re-enabling revoked old factors. They do not create another normal-login database or promise recovery of journal writes lost inside the RPO window.

## User account recovery kit

The user-facing recovery artifact is a self-contained kit containing the canonical application origin/recovery instructions, the recovery handle and all ten newly issued recovery codes. Registration, completed recovery enrollment and explicit kit rotation display it once; copy/download includes both the handle and codes, and acknowledgement refers to keeping that complete kit. Recovery must not depend on a remembered account ID, an existing session, a cookie or another value retained in the original browser. Normal authenticated responses do not retrieve old raw kit values; a user with an available passkey can rotate them. The server persists hash verifiers only, and the browser adds no silent persistent copy.

This account recovery kit authorizes the narrow recovery enrollment flow. It is separate from the operator's offline KEK/RECOVERY_KEK material: no user download contains server keys or runtime secrets, and a handle/code cannot reconstruct lost data keys. Account recovery does not change the server-readable encryption claim or repair loss of every relevant server key backup.

Required synthetic browser qualification: save the complete kit, clear cookies, sessionStorage, other site storage and in-memory state, and continue without access to an existing passkey. Enter the kit's handle and one unused code, complete enrollment of a new passkey, then verify access to the same saved reading and delivery of a replacement complete kit. Verify that the consumed code and replaced credentials cannot regain access. Exercise a codes-only artifact as incomplete recovery input. Record this as a future acceptance proof until the application journey actually runs; a contract parser alone does not establish it.

## Security mutation saga

Registration completion, passkey add/remove, recovery-code rotation/consumption, recovery-factor acknowledgement, and recovery enrollment use one operation. Ordinary passkey counter updates do not require R2; restore sets counters from the later checkpoint or zero for synchronized credentials and forces user verification, with audit of unsupported counter behavior. No bearer session is stored in the checkpoint.

1. Verify existing recent authentication or bound WebAuthn/recovery challenge entirely against current D1. Prepare the complete proposed identity state and next auth_epoch; consume challenge/code eligibility in a D1 batch with CAS. Set account.write_fence=`security:<operationId>`; create `security_operations` fenced row containing encrypted checkpoint under RECOVERY_KEK. For initial registration create a pending fenced account/key; no session/data access yet. Other credential mutations serialize on this fence, including login/recovery finishes. Existing private reads can continue only for a session still valid under current auth epoch; all personal writes/egress stop while fenced.
2. Write and confirm immutable R2 checkpoint. Its existence is the irreversible authorization commit for the already verified security mutation. A caller timeout cannot cancel it. A recovery response or new session is never issued before this point. The D1 operation is replayable if R2 succeeds but D1 is lost.
3. D1 batch asserts operation fence/epoch, applies credential/code/handle state, sets auth_epoch, invalidates old sessions and challenges, creates the permitted result session/challenge for this operation, marks applied and clears fence. Reauthorize subject before returning result. Add/remove caller may receive a replacement current session; recovery-code consumption creates only the restricted registration challenge with matching new auth_epoch. A returned `/me` CSRF token is derived from current session token, as below.
4. Cron resumes fenced/ledgered operations with the same IDs and bytes. Retry1,2,4,8,16,30min; alert at15min; never silently abandon an authorized checkpoint. Before R2 exists, a failed request has **not** completed security mutation and no privileged result may escape. After R2 exists, replay must complete it. Checkpoint data is not used to resurrect an account with an erasure intent. R2 unavailable blocks credential changes/recovery completion and first registration, not established session read access.

Every auth challenge finish compares stored auth_epoch with current account epoch and purpose/browser binding. Security operation's own consumed challenge is exempt only through its existing operation ID, not a new user-provided finish. This prevents replay of a pre-recovery credential-add challenge after takeover recovery.

## Deletion acknowledgement and lost responses

Delete requests include client-generated receiptId and random256-bit receiptToken. Client retains them in RAM and can explicitly download a receipt; server stores token HMAC only. This allows checking status after a lost response or revoked login without returning a stored secret. Duplicate request must present same receipt/body/idempotency key. Do not persist the capability silently in browser storage or put it in URLs.

D1 fence may precede R2 intent, but **HTTP202 accepting deletion is sent only after the independent intent is confirmed durable**. An R2 failure returns503 DEPENDENCY_UNAVAILABLE and retains the logical D1 fence/job; receipt status can say ledger_pending, not accepted/complete. Retry resumes that job. The status endpoint is content-free and protected by receipt token. No completed acknowledgement precedes durable erasure. An unacknowledged fence lost in catastrophic restore cannot be promised durable; report that limit, and restore preparation must flush any accessible pending fences first. Routine restore cannot begin while pending erasure/security operations exist unless their intents/checkpoints have been durably copied and verified in R2. Completion waits for all active-store erasure families, then records erasedAt and future backup expiry; while pending `backupExpiresBy:null`.

## Restore algorithm and financial fence

1. Stop all user ingress, provider egress and ledger cleanup; drain ongoing cleanup before replay. Do not expose restored DB to public routes. Preserve latest D1 bookmark/config; flush accessible pending erasure/security operations to R2; if unavailable, remain in maintenance. An unacknowledged operation that never reached independent storage is not claimed durable after catastrophic loss.
2. Restore chosen D1 bookmark. Replay every retained erasure intent using the target/pass algorithm above, including pending intents and intents whose D1 jobs did not exist at that bookmark; they take precedence over identity checkpoints. Remove erased records and copied provenance before any reads, preserving detached import tombstones. Append/resume a pass and durably complete its extended deadlines before reopening or resuming cleanup.
3. For each surviving subject, reconcile the highest authenticated identity checkpoint epoch, including one whose original D1 apply failed. Replace credentials/recovery-verifier states with this checkpoint and invalidate all sessions/challenges. Missing/corrupt checkpoints freeze identity for that subject; do not fall back to possibly revoked factors. Checkpoints do not contain DEKs: missing journal keys remains KEY_UNAVAILABLE and needs separate key recovery. If account creation/data itself was lost inside RPO, do not fabricate recovered content; explicitly recover identity to an empty account only through a separately acknowledged recovery flow after verifying available key/data inventory.
4. **Force model permission false and revoke all live context grants**, append a new permission revision above restored history, cancel all nonterminal requests regardless of whether a dispatch row is visible. Mark them blocked with recovery explanation; release held product quotas idempotently. No restored request is automatically resumed into provider dispatch. A call made after the bookmark might be absent entirely; never infer absence of execution from restored D1.
5. Freeze generation globally. Reconcile provider project usage/cost for the restored interval and UTC day/month, account for every still-uncertain ceiling, then set spend_buckets to conservative current committed totals. If exact reconciliation cannot be obtained, keep dispatch disabled or conservatively exhaust the affected day/month budget; do not reset to zero. Financial aggregates may be reconstructed from provider invoices/usage without private prompts, under a separate authorized operational action. New user starts are allowed only after this fence is explicitly cleared. A new explicit intent after recovery is a new request and may repeat a lost earlier reading; UI explains lost recovery-window work instead of promising exactly-once behavior.
6. Verify content eligibility against current repository/withdrawal manifest and erasure ledger; invalidate exports, cursors and sessions; run owned-read/save, cross-owner denial, erasure-marker and no-egress tests. Reopen saved-record access before generation if needed. Require fresh passkey sign-in for account access. Owned reads/history, Save/reflection edits, export and deletion do not require model permission; new generation after restore requires explicit model reconsent and fresh grants for any selected sources. Ordinary templates cannot bypass that permission requirement.

R2 checkpoint/intent replication, list pagination/integrity and dependency failures must be exercised in the hosted restore proof. Strong consistency is not cross-store atomicity or a substitute for checking every listed page. Monitoring tracks pending security operations as well as deletions. All new ledger families are part of export exclusion, retention and erasure coverage checks.

## Stable encrypted identity and AAD

Ciphertext includes `aadRevision`, an immutable per-field payload revision, **not current row CAS revision**. Fields tied to an immutable record use its content revision; session.question and request.input use1; request.plan uses1 because a prepared plan is immutable; dispatch.transmission/candidate use1; fragments use1; imported original bodies use1. A deliberate field replacement increments its own aadRevision and re-encrypts; ordinary save/status/lease updates do not. Rotation preserves aadRevision, changes keyVersion and authenticates both. Reconstruct AAD from record identity plus envelope aadRevision/keyVersion, never from mutable request.revision. Registry lists every encrypted field and this rule.

Generate a separate random256-bit **account index key** alongside DEK; wrap it with KEK in `account_keys.wrapped_index_key_enc` and carry the same index key across DEK versions. Private payload, intent, preview and import HMACs derive domain-separated subkeys from this stable index key. KEK rotation rewraps both. DEK rotation re-encrypts personal bodies but does not change duplicate identity. A compromised index key requires an explicit versioned HMAC reindex migration with dual lookup until every row is rewritten; not part of ordinary DEK rotation. Destroy both wrapped keys on account erasure.

CSRF token = base64url(HMAC(CSRF_SECRET, env || rawSessionToken || authEpoch)), recomputed from HttpOnly session cookie on `/me`; auth_sessions.csrf_hash records/verifies its digest. No reversible random token storage is needed. A new session/epoch changes the token; CSRF secret rotation revokes/reissues sessions. Recovery handle is returned with the codes only at initial provisioning, completed recovery enrollment or explicit kit rotation, otherwise AuthResult.recoveryHandle=null. If a new kit is needed, recent-auth code rotation issues a new handle and codes and updates their hashes/checkpoint atomically through the saga. The existing response fields form the user download; no new server-side plaintext kit store is introduced.

RECOVERY_KEK rotation re-encrypts current identity state into a new immutable checkpoint at the next serialized security epoch. Old checkpoints retain their45-day window; old KEKs and ledger HMAC keys remain longer whenever any erasure-chain object still references them. Erasure targets are immutable and use the explicit key IDs/AAD above. Identity envelope authenticity is AES-GCM plus expected key/prefix/epoch. Complete listing pagination and manifest counts are checked during restore.
