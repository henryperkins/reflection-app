# Restore invariants and the independent recovery ledger

This file is authoritative for cross-store security ordering. It qualifies the simpler D1-only state descriptions: no database restore may revive erased data, removed authentication factors, spent recovery codes, old model permission, or scheduled inference. R2 is used for **erasure receipts and encrypted identity recovery checkpoints**. It does not hold journals, prompts, account DEKs, raw recovery codes, sessions or exports. This modest expansion from erasure-only storage is a resolved review finding, justified by credential revocations that a D1 rollback would otherwise undo.

## Ledger object contracts

The runtime-authoritative shapes are ErasureIntent, ErasureCompletion and IdentityCheckpoint in DOMAIN_CONTRACTS.ts; the notation here explains their storage and ordering.

`ErasureIntentV1`: `{v:1, jobId:UUID, scope:'account'|'session'|'reflection_revision'|'context_copy', subjectHmac:hex64, targetHmac:hex64, requestedAt:UTC, operationMac:hex64}`. Immutable conditional-create object at `erasures/v1/<jobId>/intent.json`. No expiry until a completion object exists. `ErasureCompletionV1`: `{v:1, jobId, erasedAt:UTC, backupExpiresBy:UTC, purgeAfter:UTC, intentSha256:hex64, operationMac:hex64}` stored independently at the same prefix. `backupExpiresBy=erasedAt+30days`; `purgeAfter=erasedAt+45days`. Never infer completion from an intent's age. Duplicate bytes are a no-op; different bytes under a key are an incident. Ledger cleanup deletes only complete intent+completion pairs after purgeAfter. Date correction uses a new signed completion revision and keeps the latest conservative deadline.

`IdentityCheckpointV1`: encrypted operational envelope with immutable payload revision/auth epoch. Decrypted body `{v:1,operationId:UUID,subjectId:UUID,epoch:positiveInt,createdAt:UTC,recoveryHandleHash:hex64,recoveryAcknowledgedAt:UTC|null,credentials:[{id:base64url,publicKey:base64url,signCount:nonnegativeInt,backedUp:boolean,transports:string[],createdAt:UTC}],recoveryCodes:[{codeHash:hex64,usedAt:UTC|null,createdAt:UTC}]}`. Max10 credentials/10 codes/64KiB. Only hash verifiers, never raw handle/code/session/CSRF values. Key `identity/v1/<subjectHmac>/<epoch>-<operationId>.enc`; encrypt under separate RECOVERY_KEK with AAD `[env,'identity-checkpoint',subjectHmac,epoch,operationId,1]`. Latest checkpoint remains for account lifetime; superseded checkpoints retained45days then removed. Account-erasure intent overrides all identity checkpoints; erase all its checkpoints after active account erasure is confirmed (keep minimal erasure intent through backup expiry). Ledger secrets remain offline-backed-up separately from D1. No public bucket/CDN URLs.

Live authentication remains authoritative in D1. Checkpoints exist solely for crash/restore replay and contain a complete state to avoid re-enabling revoked old factors. They do not create another normal-login database or promise recovery of journal writes lost inside the RPO window.

## Security mutation saga

Registration completion, passkey add/remove, recovery-code rotation/consumption, recovery-factor acknowledgement, and recovery enrollment use one operation. Ordinary passkey counter updates do not require R2; restore sets counters from the later checkpoint or zero for synchronized credentials and forces user verification, with audit of unsupported counter behavior. No bearer session is stored in the checkpoint.

1. Verify existing recent authentication or bound WebAuthn/recovery challenge entirely against current D1. Prepare the complete proposed identity state and next auth_epoch; consume challenge/code eligibility in a D1 batch with CAS. Set account.write_fence=`security:<operationId>`; create `security_operations` fenced row containing encrypted checkpoint under RECOVERY_KEK. For initial registration create a pending fenced account/key; no session/data access yet. Other credential mutations serialize on this fence, including login/recovery finishes. Existing private reads can continue only for a session still valid under current auth epoch; all personal writes/egress stop while fenced.
2. Write and confirm immutable R2 checkpoint. Its existence is the irreversible authorization commit for the already verified security mutation. A caller timeout cannot cancel it. A recovery response or new session is never issued before this point. The D1 operation is replayable if R2 succeeds but D1 is lost.
3. D1 batch asserts operation fence/epoch, applies credential/code/handle state, sets auth_epoch, invalidates old sessions and challenges, creates the permitted result session/challenge for this operation, marks applied and clears fence. Reauthorize subject before returning result. Add/remove caller may receive a replacement current session; recovery-code consumption creates only the restricted registration challenge with matching new auth_epoch. A returned `/me` CSRF token is derived from current session token, as below.
4. Cron resumes fenced/ledgered operations with the same IDs and bytes. Retry1,2,4,8,16,30min; alert at15min; never silently abandon an authorized checkpoint. Before R2 exists, a failed request has **not** completed security mutation and no privileged result may escape. After R2 exists, replay must complete it. Checkpoint data is not used to resurrect an account with an erasure intent. R2 unavailable blocks credential changes/recovery completion and first registration, not established session read access.

Every auth challenge finish compares stored auth_epoch with current account epoch and purpose/browser binding. Security operation's own consumed challenge is exempt only through its existing operation ID, not a new user-provided finish. This prevents replay of a pre-recovery credential-add challenge after takeover recovery.

## Deletion acknowledgement and lost responses

Delete requests include client-generated receiptId and random256-bit receiptToken. Client retains them in RAM and can explicitly download a receipt; server stores token HMAC only. This allows checking status after a lost response or revoked login without returning a stored secret. Duplicate request must present same receipt/body/idempotency key. Do not persist the capability silently in browser storage or put it in URLs.

D1 fence may precede R2 intent, but **HTTP202 accepting deletion is sent only after the independent intent is confirmed durable**. An R2 failure returns503 DEPENDENCY_UNAVAILABLE and retains the logical D1 fence/job; receipt status can say ledger_pending, not accepted/complete. Retry resumes that job. The status endpoint is content-free and protected by receipt token. No completed acknowledgement precedes durable erasure. An unacknowledged fence lost in catastrophic restore cannot be promised durable; report that limit, and restore preparation must flush any accessible pending fences first. Routine restore cannot begin while pending erasure/security operations exist unless their intents/checkpoints have been durably copied and verified in R2. Completion waits for all active-store erasure families, then records erasedAt and future backup expiry; while pending `backupExpiresBy:null`.

## Restore algorithm and financial fence

1. Stop all user ingress and provider egress. Do not expose restored DB to public routes. Preserve latest D1 bookmark/config; flush accessible pending erasure/security operations to R2; if unavailable, remain in maintenance. An unacknowledged operation that never reached independent storage is not claimed durable after catastrophic loss.
2. Restore chosen D1 bookmark. Replay all unexpired erasure intents, including pending intents without completion; they take precedence over identity checkpoints. Remove erased records and copied provenance/import aliases before any reads. Refresh erasedAt/completion conservatively if replay creates a new active-store erasure boundary.
3. For each surviving subject, reconcile the highest authenticated identity checkpoint epoch, including one whose original D1 apply failed. Replace credentials/recovery-verifier states with this checkpoint and invalidate all sessions/challenges. Missing/corrupt checkpoints freeze identity for that subject; do not fall back to possibly revoked factors. Checkpoints do not contain DEKs: missing journal keys remains KEY_UNAVAILABLE and needs separate key recovery. If account creation/data itself was lost inside RPO, do not fabricate recovered content; explicitly recover identity to an empty account only through a separately acknowledged recovery flow after verifying available key/data inventory.
4. **Force model permission false and revoke all live context grants**, append a new permission revision above restored history, cancel all nonterminal requests regardless of whether a dispatch row is visible. Mark them blocked with recovery explanation; release held product quotas idempotently. No restored request is automatically resumed into provider dispatch. A call made after the bookmark might be absent entirely; never infer absence of execution from restored D1.
5. Freeze generation globally. Reconcile provider project usage/cost for the restored interval and UTC day/month, account for every still-uncertain ceiling, then set spend_buckets to conservative current committed totals. If exact reconciliation cannot be obtained, keep dispatch disabled or conservatively exhaust the affected day/month budget; do not reset to zero. Financial aggregates may be reconstructed from provider invoices/usage without private prompts, under a separate authorized operational action. New user starts are allowed only after this fence is explicitly cleared. A new explicit intent after recovery is a new request and may repeat a lost earlier reading; UI explains lost recovery-window work instead of promising exactly-once behavior.
6. Verify content eligibility against current repository/withdrawal manifest and erasure ledger; invalidate exports, cursors and sessions; run owned-read/save, cross-owner denial, erasure-marker and no-egress tests. Reopen saved-record access before generation if needed. Require fresh passkey sign-in, explicit model reconsent and new source grants after restore.

R2 checkpoint/intent replication, list pagination/integrity and dependency failures must be exercised in the hosted restore proof. Strong consistency is not cross-store atomicity or a substitute for checking every listed page. Monitoring tracks pending security operations as well as deletions. All new ledger families are part of export exclusion, retention and erasure coverage checks.

## Stable encrypted identity and AAD

Ciphertext includes `aadRevision`, an immutable per-field payload revision, **not current row CAS revision**. Fields tied to an immutable record use its content revision; session.question and request.input use1; request.plan uses1 because a prepared plan is immutable; dispatch.transmission/candidate use1; fragments use1; imported original bodies use1. A deliberate field replacement increments its own aadRevision and re-encrypts; ordinary save/status/lease updates do not. Rotation preserves aadRevision, changes keyVersion and authenticates both. Reconstruct AAD from record identity plus envelope aadRevision/keyVersion, never from mutable request.revision. Registry lists every encrypted field and this rule.

Generate a separate random256-bit **account index key** alongside DEK; wrap it with KEK in `account_keys.wrapped_index_key_enc` and carry the same index key across DEK versions. Private payload, intent, preview and import HMACs derive domain-separated subkeys from this stable index key. KEK rotation rewraps both. DEK rotation re-encrypts personal bodies but does not change duplicate identity. A compromised index key requires an explicit versioned HMAC reindex migration with dual lookup until every row is rewritten; not part of ordinary DEK rotation. Destroy both wrapped keys on account erasure.

CSRF token = base64url(HMAC(CSRF_SECRET, env || rawSessionToken || authEpoch)), recomputed from HttpOnly session cookie on `/me`; auth_sessions.csrf_hash records/verifies its digest. No reversible random token storage is needed. A new session/epoch changes the token; CSRF secret rotation revokes/reissues sessions. Recovery handle is returned only at provisioning/rotation, otherwise AuthResult.recoveryHandle=null. If a new handle is needed, recent-auth code rotation issues a new handle and updates its hash/checkpoint atomically through the saga.

RECOVERY_KEK rotation re-encrypts current identity state into a new immutable checkpoint at the next serialized security epoch, then retains old checkpoints/KEKs through their45-day window. Pending erasure target envelopes are re-encrypted with stable aadRevision under the new operational key before old-key removal. Key loss never authorizes accepting an unverified checkpoint. Checkpoint operationMac is HMAC over JCS of all public intent/completion fields except operationMac; identity envelope authenticity is AES-GCM plus expected key/prefix/epoch. Complete listing pagination and manifest counts are checked during restore.
