## Canon, review and release lifecycle

Canonical source format is `CanonSource` in DOMAIN_CONTRACTS. Identity includes immutable source ID/version/hash, card/orientation/optional position, exact prose/fallback/question, traditional interpretation kind, rights evidence/territory/attribution and explicit review kind/reviewer/time/reviewedHash. `ContentBundle` contains the ordered78-card edition identity and at least156 approved neutral interpretation entries (78×2), plus separately versioned position/copy resources in its release manifest. Bundle hashing uses JCS excluding only editionHash; all actual source/render/copy bytes and deck mapping enter identity. Do not hash only a label/version and later change text behind it.

Initial content is newly selected/edited minimal English canon. Every source selected for launch and its fallback/questions has explicit human approval and cleared rights. Agent-reviewed predecessor copy is eligible for evaluation/reference, not production approval until the exact transformed bytes are reviewed. A human-reviewed historical example does not confer approval on model variants. Reviewer identity can be an owner pseudonym in repository; approvals record Git SHA plus content hash and rubric. A repository signature/commit is attribution, not a claim of source truth.

Lifecycle: staged → reviewed approved → active pointer; old active becomes superseded (still eligible historically/in-flight unless withdrawn); withdrawn never automatically reactivates. Activation uses one D1 batch: assert expected system revision/current hash; assert new content hash/rights/human review match immutable repository bundle; change pointer, increment system revision, mark prior approved edition superseded. Concurrent activation loser409. Stage idempotently by hash; same hash/different bytes is integrity failure. Runtime generation reads active pointer and bundle once into PreparedPlan. Publication checks captured content policy revision/eligibility, not merely that some active content exists.

Rollback explicitly activates an earlier still-cleared reviewed edition with new pointer revision; never edits content bytes or historical readings. Withdrawal types: editorial improvement → supersede only, old accepted text labeled edition; false/dangerous claim or rights withdrawal → set withdrawn, policy revision++, stop new/in-flight use and suppress affected historical text; when text must be erased, run erasure ledger over affected reading/source copies. User-authored responses remain separately accessible. Export indicates removed source/body and reason. Reproduction is best-effort subject to correction/erasure, not an entitlement to retain forbidden text forever.

Keep source decisions, prompt/validator schemas, source release manifests and small synthetic eval fixtures in Git. Bulk synthetic eval outputs may be encrypted owner-local files with SHA manifest and90-day retention; private historical examples are excluded unless explicit rights/privacy authorization is obtained. No new online artifact service is required. No production sampling by default; evaluation review scores never create human approval.

## Canonical portable format and selected adapters

Authoritative types: `LegacyRecord`, `PortableRecord`, `ExportPage`, `ImportWrite`, `ImportPreview`, `ImportResult`. `reflection-export.v1` is UTF-8 NDJSON, one ExportPage per line, in ticket/cursor order. Each page has same export ID/snapshot revision, UTC exportedAt, ≤100 records and ≤1MiB. Record variants are session, reading (including unavailable tombstones), reflection revision, revisit, generation receipt, permission and grant. Permissions and grants are paginated PortableRecord variants; first page has bounded account/credential metadata and subsequent pages account=null; no secrets/key material. Account export includes accepted and imported bodies, basis, provenance, user-authored revisions/stances, selected/transmitted context where retained, numeric usage and explicit redaction. It excludes rejected private candidates, internal security hashes and unselected raw credential material. Export can fail if current permission/source deletion changes data revision; user restarts instead of getting an inconsistent mixture.

Client bounds each upload chunk to the import document200k-character/2MiB limits; canonical records are not split inside a string. Native generated record cap64KiB; legacy normalized record+exact JSON cap192KiB UTF-8. A source record exceeding192KiB is an explicit per-item error with local export preserved, never truncated. Large exports are imported as ordered chunk batches. `source_key_hmac=HMAC(owner,source namespace + originalId + record kind + revision)` prevents duplication across batches; originalHMAC binds exact raw canonical record bytes. Parent aliases may resolve in later chunks, but commit of a session group waits for every required parent/reference; unresolved groups stay preview/failed with missing-parent message, never silently reparent.

For `reflection-import.v1`, a document is `{format:'reflection-import.v1', records: LegacyRecord[]}`. It is an import adapter envelope, not a direct generation contract. LegacyRecord preserves exact old generated/user text, exact original JSON as a UTF-8 string, original SHA256, timestamp string and parsed UTC nullable, original ID/parent, known card/source IDs, raw basis and explicit gap flags. JSON string parse preserves textual content; the raw record bytes and SHA preserve lexical formatting. Unknown timezone/units leave occurredAt null. No new timestamp, deck or generation identity is substituted. importedAt is a distinct successor event.

## Retirement branches and dependency order

Nothing is shut down or billed by this task. Inventory actual projects before choosing a branch: deployed services/domains, data stores/keys/backups, account counts/activity, auth providers, paid subscriptions/invoices/refunds, external integrations, support promises and asset obligations. Gather only authorized read-only facts; unanswered counts are unknown, not zero.

| Verified situation | Required decisions/evidence before shutdown |
|---|---|
| No real users, no paid obligations | Owner confirms inventory and no recoverable personal records/active subscriptions. Export relevant code/content/assets and key decisions; disable new writes/generation before removing dependent services. Retain only necessary legal/operational records. |
| Free users | Owner-approved notice/support/recovery window; working user export and demonstrated decrypt/restore; optional migration preview/acceptance with independent ownership proof. Stop enrollment, then new generation, keep read/export/recovery/delete available through stated window. Never force migration to get deletion. |
| Paying subscribers | Reconcile billing provider subscriptions/invoices/refunds and terms first; owner decides service continuation, cancellation, notice/refund/proration/support obligations. Do not equate disabled UI billing with stopped renewals. Verify required communications and financial handling completed before ending entitlement/service. Successor quotas grant no automatic substitute contract. |

Shutdown dependency order: billing/identity/data obligations inventory → tested export/recovery and approved communications → stop new enrollment/renewal as explicitly decided → stop new generation and drain/fence jobs → migration acceptance where chosen → preserve read/export/delete/recovery until deadline → verify zero active obligations/unresolved jobs → revoke inference/integration keys → remove compute routes → erase personal stores with backup/receipt policy → retire auth, databases and domains last when recovery/support no longer depends on them. This order is a proposed dependency map, adjusted only by verified facts. Preserve migration manifest hashes and acceptance receipts without raw private records. Real export availability is not a launch dependency for the successor's synthetic-tested import capability.

Import identity rows map each source key to a typed owned session/edition/reflection revision/revisit, with composite FKs; receipt/permission/grant records remain historical imported metadata and create no live authority. source_record_enc preserves the exact PortableRecord/normalized original for round-trip export and is included in copy erasure. Resolve a child only through a matching entity_kind plus exact mapped ID/revision; a matching session alone is insufficient. Missing aliases remain unresolved, never inferred. Erased identity tombstones retain source_key_hmac with source_record_enc=null to prevent accidental resurrection by re-import; an explicit new import after deletion requires a new source namespace and clear user warning.

CanonSource.hash is SHA256(JCS of id, version, kind, cardId, orientation, position, text, fallbackText, reflectionQuestion and rights)); exclude hash and review to avoid self-reference. review.reviewedHash must equal that digest. ContentBundle.editionHash covers the complete bundle except editionHash, including source review records, deck mapping, positionFrames and productCopy. Bundle-level human approval in content_editions binds its full edition hash. Deck hash is SHA256(JCS(ordered deck entries)); name/art/attribution changes produce a new deck edition.
