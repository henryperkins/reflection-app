# Identity, privacy, operations and release policy

All targets and procedures are proposals. Secret values, resource IDs, jurisdictions and hosted proof results are external inputs. No live configuration was changed for this package.

## Threat model and trust boundaries

Protect questions, reflections, selected context, draws/derived facts, import records, accepted text and access credentials. Threats: another user guessing IDs; cross-site requests; malicious imported/model text; stolen sessions/recovery factors; logging/analytics leakage; untrusted preview code; a provider retaining authorized text; stale jobs after cancellation/rotation; backup restoration resurrecting erased data; operator errors. The browser, imports, model outputs and external content are untrusted. D1 metadata still reveals timing, relationships and account activity even when bodies are encrypted.

Trust owner-controlled Worker code and its runtime secrets to decrypt authorized records. This is **server-readable encryption, not end-to-end encryption**. A compromised Worker or sufficiently privileged operator can access plaintext. Launch, setup and privacy copy must state that records are encrypted in storage and the service can decrypt them for authorized operations; it must not promise that only the user can read them or that the operator has no access. D1 compromise without Worker secrets is a different threat; envelope encryption reduces its impact. Neither encryption nor a fact citation makes generated advice reliable. Avoid a second plaintext search index, analytics dataset, model memory store or personal-content cache.

## Identity and sessions

Select passkeys with `@simplewebauthn/server`/`browser` (maintained v14 API family), verified in workerd before rollout. Library handles WebAuthn challenge, RP/origin, signature and user verification; application handles authorization, session/recovery and single-use DB races. Do not implement cryptography manually. Enable `nodejs_compat` only as needed by the pinned library, test the exact compatibility date, and pin it with the lockfile. The [official server documentation](https://simplewebauthn.dev/docs/packages/server) documents Node/Deno; Worker compatibility remains a qualification gate.

No email, legal name, phone, password, social identity or marketing identifier is collected. Each account has a UUIDv4 internal subject. Passkey credential IDs may change while ownership stays on the internal subject. For registration preallocate the subject UUID as the registration challenge ID, encode its 16 bytes as WebAuthn user.id, and use a random display alias `Reflection account <short handle>`. No user-private question becomes the authenticator label. RP ID is the exact production domain chosen before launch; expectedOrigin is a single exact HTTPS origin. Preview and local RP IDs are separate. Migration to an unrelated domain requires explicit credential enrollment while the old domain still works.

1. `/auth/options` creates a 256-bit challenge, stores its keyed hash with purpose, five-minute expiry and browser-cookie hash. Set `__Host-challenge`, Secure, HttpOnly, SameSite=Strict, Path=/, Max-Age=300. Store no private record before registration completes. Limit 10 challenges/10 minutes/IP and 3 registrations/day/IP; generic failures avoid account enumeration. IP rate keys are daily HMACs, not raw addresses, retained ≤48 h.
2. Register with residentKey required, userVerification required, attestation none; permit ES256 (-7) and RS256 (-257). Verify clientData type/origin/challenge, rpIdHash and library signature/attestation checks; reject extra transports/extensions not requested. Use the security checkpoint saga: a fenced D1 batch creates account, DEK/index key, credential proposal and initial **modelAllowed=false** permission; issue a session only after checkpoint durability and final D1 apply. Concurrent challenge reuse fails CHECK/UNIQUE. This is the first account persistence.
3. Authentication is discoverable-passkey login. Resolve credential ID to internal subject, validate active account, verified userHandle equal to subject bytes, signature and UV; challenge purpose must match. Library counter checks support synchronized passkeys with zero counters; suspicious positive-counter rollback denies and offers recovery. Counter update and challenge consumption are atomic. No automatic linking based on labels or guessed identity.
4. Cookie `__Host-session`: 32 random bytes, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. Store HMAC-SHA256(token) only. Absolute expiry 7 days, idle expiry 24 h; last-used writes at most every 5 minutes. Validate account auth_epoch each request; cache it nowhere across requests. Recent auth lasts 5 minutes for credentials, recovery codes, export initiation and account erasure. Rotate session token on login/recovery and privilege changes. Expired session returns 401; owned in-progress work may finish if account permission stays valid, but UI requires login to observe it.
5. CSRF: strict Origin equality on every mutation, require JSON content type and `X-CSRF-Token` matching the deterministic session-bound HMAC token (digest stored; derivation in SECURITY_RESTORE). Reject missing/mismatched Origin, `Sec-Fetch-Site: cross-site`, and wildcard CORS; cross-site GET cannot mutate. Challenge-auth endpoints require same origin and challenge cookie instead of session CSRF. CSRF token returned by `/me`; never in URLs. Set CSP without unsafe-inline/eval, `frame-ancestors 'none'`, `object-src 'none'`, HSTS after stable HTTPS, Referrer-Policy no-referrer, Permissions-Policy disabling unneeded sensors. Escape all private text; no HTML import rendering.
6. Credential add/remove requires recent existing passkey reauthentication. Limit 10 credentials, cannot remove the last one; recovery enrollment replaces credentials in a separate flow. Credential changes use the security checkpoint saga, increment auth_epoch and revoke all other sessions. No shared-account merging in v1. Logout deletes current session before 204; logout-all increments auth_epoch/deletes all sessions. Clear client memory, query caches, sessionStorage intent IDs and any stale private caches; BroadcastChannel signals other tabs.

Account recovery kit: registration, completed recovery enrollment and explicit rotation return a complete kit once: an unguessable recovery handle (separate random 128 bits), ten independent 128-bit random recovery codes, the canonical application origin/recovery instructions, and a clear statement that recovery requires the handle plus one unused code. Show/copy/download the handle and codes together; a codes-only download is incomplete. Require the user to acknowledge keeping the complete kit before first personal reading. The handle and codes are secrets; persist only keyed hash verifiers and code used_at, never their plaintext or reversible ciphertext. The kit stays in client RAM until an explicit copy/download, with a shared-device warning; no silent browser or server copy is added. If it is lost, use an available passkey to rotate the kit rather than retrieving old plaintext. This user kit is separate from operator KEK recovery material and contains no server encryption keys or runtime secrets.

A handle plus one unused code uses the security checkpoint saga to consume the code, increment auth_epoch and revoke sessions before issuing a browser-bound recovery registration challenge; every challenge finish checks current auth_epoch. No authenticated personal-content access is granted by this narrow recovery challenge. Finishing a valid new passkey in five minutes deletes prior credentials and recovery codes, enrolls the new credential, issues a new complete kit and a session. An abandoned recovery leaves remaining codes and existing passkeys usable; it does not expose data. Rate limit five failures/hour/IP and handle, generic error. No support bypass: recovery requires an available passkey or the recovery handle plus an unused code. The server-readable DEK remains available after proven recovery; a new credential does not silently rekey/lose data. Qualification must demonstrate recovery using only the saved kit after browser state has been cleared and without an available existing passkey, as specified in SECURITY_RESTORE.

## Encryption and key lifecycle

Use Web Crypto AES-256-GCM with fresh 96-bit cryptographically random nonce per encryption; 128-bit tag; no homemade cipher/PRNG. Per-account random DEK encrypts all personal bodies. Environment KEK wraps DEKs using AES-GCM; KEK lives only in Worker secrets and offline encrypted operator recovery material. Cipher envelope `{v:1,alg:'A256GCM',keyVersion,aadRevision,nonce,data}` uses base64url. AAD is canonical UTF-8 JSON array `[environment,table,column,ownerId,recordId,aadRevision,cipherVersion,keyVersion]`; each composite-row recordId has a specified stable encoding `id:revision` or `requestId:ordinal`. aadRevision is immutable per encrypted payload and distinct from row CAS revision; exact field rules are in SECURITY_RESTORE. Wrap AAD includes environment, account and key version. Nonce/tag decoding lengths and ciphertext size limits are enforced before decrypting. Authentication failure is corruption/KEY_UNAVAILABLE, never an empty value.

Credential/session/recovery/IP/idempotency HMACs use separate domain-separated secrets or HKDF subkeys, not the data DEK. Private payload identity uses a separately wrapped stable account index-key HMAC with separate purpose (see SECURITY_RESTORE), never an unkeyed public hash of a low-entropy question. Public content uses SHA-256 JCS. User grants permit access; knowledge of a ciphertext, hash or UUID does not.

KEK rotation: add new KEK secret/version, unwrap then rewrap each DEK with CAS on wrap_key_id, verify decrypt, retain prior KEK through 30-day database recovery window plus 7-day margin, then remove using a recorded operator operation. Rewrap changes only account_keys, not every private body. Do not log key material. To rotate a compromised account DEK: set account.write_fence to an operation UUID, increment run fences, block new personal writes/egress, allow read/export only with verified available old keys; create next DEK version; re-encrypt every registry field in batches with deterministic progress from remaining old key_version rows; verify no old rows, update account.key_version and clear fence atomically. Old key rows remain until no references; DB FK prevents accidental destruction. A crash resumes the scan. No mixed write versions enter one operation. Export cursors invalidate on the data revision change. Account status frozen/write_fence surfaces “temporarily read-only”, not data loss.

Account deletion destroys wrapped DEKs only after active data is removed and durable erasure receipt recorded. Backups may contain old wrapped DEKs plus still-recoverable KEKs; **do not claim immediate irreversible cryptographic deletion of backups**. Restore always runs disconnected, replays erasures, and only then receives active secrets and user traffic. Last KEK destruction cannot precede the retained backup window for remaining accounts. Loss of every KEK backup is permanent data loss; recovery codes do not reconstruct cryptographic keys.

Unsubmitted question and reflection drafts remain in browser RAM. **Start** explicitly authorizes the disclosed temporary encrypted server storage needed to process and recover the request; successful Start creates an unsaved session with a 24 h deadline, and the accepted reading remains in that session. **Save** removes that temporary expiry and keeps the reading until deletion, subject to existing erasure/withdrawal rules. Explicit Unsave returns the session to a new 24 h window. Save does not require a written reflection, stance or disagreement; it must not create an empty authored reflection. Writing a reflection is optional. An explicit reflection-save action atomically saves the reading as already specified, and its label must explain that combined effect. Confirmed import separately authorizes keeping the selected records; an import preview retains its existing 24 h limit.

Model permission is `permission_revisions.model_allowed` under a visible `egress.v1` notice; first default is false. Start's storage disclosure, Save, a reflection save and import never enable it implicitly. With model permission off, normal ownership/authentication/key checks still permit reading and reopening saved records, available history, saving an existing reading, authoring/editing reflections, export and deletion. New AI starts and follow-ups are blocked, and an ordinary fallback/template reading cannot bypass missing or revoked permission. Turning permission off does not erase saved records or make model reconsent a prerequisite for those non-generation actions.

Source eligibility is a current grant for a specific reading edition or reflection revision. Selection is a user-chosen code-point range with exact preview hash. Transmission is the actual encrypted payload plus digest in provider_dispatches. Temporary storage, saved retention, model permission, source eligibility, selection and transmission are distinct records/actions, not overloaded booleans. An imported reading has no grant. A new reflection revision revokes grants on superseded revisions; old revision may remain viewable but is ineligible for future dispatch unless the owner deliberately re-establishes it as a new current authored statement. Accepted generated text is labeled generated when selected, never remembered biography.

Revocation increments account permission revision or grant revision and fences all affected nonterminal requests in the same D1 batch. Dispatch authorization before the revocation means text may already have left; a provider cannot be made to forget through a DB update. Publication is still blocked. Plain revocation stops future use, while “erase this source and shared copies” also removes downstream snapshots. Copy erasure replaces selected-fragment text/hash with null and `availability:'erased'`, removes exact payload/plan/candidate ciphertext and marks reproduction incomplete. If output itself quotes or substantially depends on the erased material and removal cannot be isolated reliably, withdraw its accepted body conservatively and preserve only an unavailable tombstone; do not auto-rewrite history. Independent user-authored reflections remain unless selected for deletion. Clear UI/export redaction reason, no manufactured historical evidence.

## Erasure saga and restore safety

Delete account requires recent auth plus explicit UI confirmation; no administrative billing dependency. Delete a session requires auth, CSRF, matching revision; delete a reflection revision requires owning its parent and matching current metadata. Use a small tombstone for broken references; foreign owners still see 404. The operation is idempotent, keyed and irreversible after the fence. Return a receipt token that can query only coarse deletion status after sessions are revoked; its hash is stored, it grants no reading access.

The authoritative ordering and exact R2 object schemas are in [SECURITY_RESTORE.md](SECURITY_RESTORE.md). D1 fences access first; deletion HTTP202 is returned only after an independent erasure intent, including its encrypted minimal target, is durable. Client-supplied receipt ID/token permits status recovery after lost responses without keeping a raw server secret. R2 failure returns503 and leaves an unacknowledged fenced job pending; it does not claim durable acceptance. Physical active-store erasure may follow asynchronously, target24h. While any pass is pending, backupExpiresBy is null. First completion sets erasedAt+30days and ledger retention to erasedAt+45days; later restore passes append completion revisions and can only extend these deadlines. Pending intents/passes never expire. Replay uses retained key IDs and the R2 target even when the D1 job is absent.

Security credential changes/recovery also use the specified fenced D1 → encrypted R2 checkpoint → D1-apply saga. No new privileged session or recovery grant escapes before its checkpoint. Runtime auth remains in D1; current factor snapshots exist outside its rollback domain so restoring a backup cannot revive removed factors or spent recovery codes. Checkpoints hold public verification keys and hashed recovery verifiers, not raw factors, user text or data keys.

Restore remains offline until all erasures and latest authenticated identity checkpoints are replayed. Invalidate every session/challenge/export ticket, force model permission false, revoke all context grants, and terminalize **all** restored nonterminal generation requests regardless of visible dispatch rows. Keep dispatch disabled until provider liability/spend for the restored interval is reconciled conservatively. A lost dispatch row is not evidence of no external execution. Reopen saved records only after key, ownership, content and erasure checks. Fresh sign-in is required for account access; new generation additionally requires model reconsent and fresh grants for any selected sources. Owned reads/history, reflection editing, export and deletion remain available with model permission off once their normal service checks pass. Source/body corrections can make historical reproduction incomplete.

The system does not offer protection against simultaneous total loss of both Cloudflare data and all offline KEKs, nor guarantee remote deletion on disconnected browsers/provider retention stores. State these limits without converting them into blanket reasons to block coding.

## PWA and device privacy

Service worker allowlist: hashed JS/CSS, fonts, manifest, generic icons, licensed card art and a static offline page. Never cache `/api/**`, navigation responses containing personal content, auth routes, exports or private error responses; network handlers set `Cache-Control: private, no-store`, no CDN caching. Static shell contains no inline personal JSON. Do not cache requests/responses merely because HTTP status is 200. No Background Sync for private mutations; no offline drafts or optimistic “saved” badge. Offline editing remains in RAM while tab lives, with explicit “unsaved; will be lost on reload” notice and optional user-initiated download/copy.

On logout clear memory/query caches, call service-worker purge of any non-allowlisted entries, clear intent IDs, navigate to signed-out route, notify other tabs; use Clear-Site-Data for appropriate caches/storage where supported, but cookies/session revocation is server-authoritative. Revalidate identity on tab focus and before showing resumed private content; blank on 401 or user switch. Hide sensitive content in shared-device mode when tab becomes hidden; unlocking requires reauth. Installation requests no new private persistence permission. Browser bfcache can retain a screen briefly; pageshow must blank then reauthorize before display. OS screenshots, downloaded exports, browser extensions and disconnected tabs are beyond a promise of remote erasure.

## Language, sensitive topics and egress controls

English is supported. Ask user to confirm English output; local language detection is a hint with uncertainty, not a truth label. Short/ambiguous text is `unknown`; show an English confirmation step, do not silently translate. Confident non-English request → 422 UNSUPPORTED_LANGUAGE with owner-approved English copy offering rephrasing or a memory-only private draft with explicit copy/download, without a server save or generation. No unchecked translated response. Output language detector plus schema/lexical review rejects unsupported prose. Content versions include the exact approved language/fallback/crisis strings.

Local input analysis uses sentence/context categories (direct self-harm intent, figurative loss, uncertain risk, regulated advice request), not a keyword ban. “What unconscious patterns keep me stuck?” is ordinary reflection. “Why do I keep bleeding money?” is figurative financial distress: allow reflective framing, forbid prescriptive financial recommendations. “I want to end my life” yields a **non-reading** supportive response; no tarot, model call or ordinary template. Proposed copy for editorial approval: “I'm sorry you're facing this. If you might act on these thoughts now, contact local emergency services or someone you trust who can stay with you. This reading tool cannot provide crisis care.” Region-specific contacts require owner geography and maintained source approval. No location inference from birth data/IP and no fabricated local numbers.

Uncertain risk shows supportive clarification and allows the person to edit in RAM and explicitly copy/download locally; no server save is promised without a reading; no remote human review in v1. Do not automatically notify third parties. A user can correct a false positive by rephrasing; an “I consent” checkbox cannot bypass an explicit imminent-risk outcome. Diagnosis/treatment/legal/financial action requests return an approved non-reading boundary message and a neutral journaling invitation. Safety copy is maintained/versioned with content, reviewed at least quarterly and on a reported issue. The limited local classifier has residual false-negative/positive risk; balanced qualification measures both. Provider refusal is separately surfaced without attempts to persuade the provider or user.

Runtime egress allowlist: `https://api.openai.com:443/v1/responses` POST only; redirects error; no user-controlled hostname, proxy, tools or remote schema reference. WebAuthn is browser/local cryptography, no authenticator cloud API called by this service. D1/R2 use bindings; no public HTTP database adapter. Static dependencies are bundled; no third-party analytics/font CDN. Future calculation provider requires a separate declared allowlist/consent before use. Tests plant unique markers in unselected reflections, other accounts, raw import fields, recovery secrets, diagnostics, file names and source instructions; intercept every fetch and assert absence in body/headers/URL/errors/logs. Selected marker appears only in its authorized payload, not provider metadata.

## Secrets, configuration and failure isolation

Production runtime secrets: KEK versions, independent RECOVERY_KEK versions, session/CSRF/recovery/ledger HMAC material, provider project API key. Separate preview secrets and resource accounts, no reuse. Build credentials may deploy code and therefore indirectly access runtime secrets: treat production builds as privileged. Store build deploy token separately from runtime provider keys; local developers get synthetic credentials. Pin origin/RP, D1/R2 binding IDs, provider/model/schema hashes, price policy, generation enabled flag and content pointer. No default-to-production origin or account ID.

Missing KEK disables encrypted reads/writes for affected version; missing provider key disables dispatch, with a clearly indicated approved outage template only if generation permission/plan/content are valid. Missing R2 or recovery KEK blocks registration, security mutations, durable deletion acceptance and restore; existing saved-record access can continue with valid sessions and data keys. Missing origin/session secret disables authenticated routes. Static help and health remain available where safe. Startup/health checks report **names** of missing configuration, never values. Revoke/rotate provider keys on exposure; freeze dispatch, preserve known costs, requalify a provider policy change. Local checks never require or load real secrets.

## Hosted release and migration enforcement

Repository-owned future command `npm run verify`: locked clean install assumptions, formatting/lint, strict TS, generated-schema drift, registry coverage, Vitest deterministic/domain/DB/fault/privacy tests, actual migrations in Workers pool, build, and bounded Playwright+axe synthetic journeys. Provider network is intercepted and denied by default; any attempted real URL fails the gate. Live model/editorial studies are separate artifacts and launch gates, not nondeterministic release tests.

Workers Builds configuration proposal:

|---|---|---|
| Account and Worker | Dedicated production account/Worker; resource IDs supplied later | Separate Cloudflare account with no production trust/keys/data |
| Trigger | Only protected `main` | Explicit reviewed branch allowlist; untrusted forks not automatically executed with credentials |
| Build command | `npm ci --ignore-scripts && npm run verify` | Same deterministic gate with synthetic fixtures |
| Deploy/preview command | `npm run release:production` | `npm run release:preview` |

| Install scripts | Dependencies needing scripts explicitly allowlisted and executed after audit; no blanket install-script privilege | Same policy |
| Credentials | Least-privilege production deployment/migration token; no provider/KEK in build env | Token scoped only to separate preview account, synthetic keys |

The gate writes a local verification receipt of commit/lockfile/config/schema hashes and pass state. It is a consistency check, not a cryptographic defense against malicious main code editing its own tests. Build scripts and release wrapper are CODEOWNERS-reviewed. Cloudflare dashboard build settings, default deploy command and custom Wrangler build settings are distinct; configure the actual hosted build/deploy commands. Disable direct default deploy hooks and automatic main promotions outside the wrapper. A retried build uses current settings, so include a settings audit in release proof.

Workers Builds documents a 20-minute hard timeout; proposed verify p95 8 minutes, 9-minute gate deadline leaves deployment margin. Current paid plan includes 6,000 build minutes/month. GitHub required review/branch protection is **merge enforcement**; the Cloudflare build/deploy sequence is **deployment enforcement**. Branch rules may depend on repository/account availability; inspect them during setup. A failed main build must leave last good production serving even if the commit merged. Bypass paths: Cloudflare dashboard edit/deploy, API token/CLI, altered build settings, owner branch-rule override, malicious main scripts, migration token use. Restrict owner/admin access with MFA, remove unused tokens, review audit log; cannot claim the sole owner is technically unable to bypass.

Preview commands/defaults evolve; do not rely on a version URL to isolate data. Current docs warn version URLs use configured resources. Even branch-isolated preview resource features are not trusted as the only boundary: the separate account and synthetic provider configuration contain untrusted code. Build tokens can access their account; no production token enters preview. Confirm actual bindings and a planted production-only marker exclusion before rollout. No predecessor secrets/data are copied.

Required hosted proof (not run here): configure synthetic staging equivalent to production; deploy good SHA A, then intentionally failing deterministic test at SHA B; verify build fails before migration/deploy and serving SHA remains A. Repeat bypass attempt from a non-main branch with the production command; assert early rejection before any mutation. Verify preview cannot read production marker/binding, build output hides secrets, and reverting B restores green promotion. Store logs/config fingerprint/artifact hashes and observed serving SHA. Then run the same controlled failing-test proof against the actual main release path before first real users, using no personal data. If platform cannot enforce the build→deploy ordering, stop launch and select another hosted runner; no GitHub Actions substitution.

Migrations: additive **expand → dual-compatible deploy → backfill → verify → contract**. Deploy N and N−1 remain readable/writable through expansion; no new required non-default column while N−1 may run. Feature flag new writes until all active versions understand both. Backfill idempotently with owner-key fences and bounded batches. Minimum compatibility window two successful releases plus seven days and a tested rollback, AND expiry/migration of all pending request/decoder versions. Destructive contract steps require no old active Workers/jobs, backfill coverage, restore proof and explicit owner release decision; they do not run automatically with every build. Code rollback to compatible N−1 uses existing expanded DB. Persistent data rollback is the separate offline erasure-aware restore procedure. Content rollback activates a reviewed immutable edition via CAS; it never rewrites saved output.

## Monitoring and runbooks

Use Worker platform metrics/logs with a strict serializer, not raw fetch logs. Metrics: API latency/errors; oldest pending age; nonterminal count; attempt epochs; accepted/model/template/refusal/blocked rates; quota holds; reserved/actual/unknown provider cost; D1 rows read/written/storage; erasure age; key unwrap failures; gate duration; content edition IDs. No private content sampling. Correlation UUID per request is safe to show support, with seven-day logs. Diagnostics toggle for 15 minutes may increase **content-free** transition/error detail only, never print decrypted values. User exports are the only v1 way to share private material deliberately outside the service.

Set `observability.logs.invocation_logs=false` because automatic invocation messages include request URLs; use only the allowlisted custom serializer and sanitized caught errors. Paid Workers Logs currently retains seven days, with an announced pricing change on2026-12-01; the cost estimate is dated and must be refreshed for later rollout. No extra logging service is selected. Thirty-day operational summaries are aggregate counts only, exported locally by the operator from platform metrics; the system does not assume log events remain queryable after seven days. [Official logging controls](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).

## Cost model and future entitlement boundary

Prices sourced 2026-10-26; estimates exclude tax, domain registration, legal/editorial labor and any paid repository plan. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) includes $5/month minimum, 10M requests and 30M CPU-ms, then $0.30/M requests and $0.02/M CPU-ms. [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) includes 25B rows read, 50M rows written and 5 GB on paid, then $0.001/M reads, $1/M writes and $0.75/GB-month. These are service-specific prices, not measured usage.

Planning envelope: 100k dynamic requests plus ~43,200 monthly minute Cron wakes, 10ms/request average CPU assumption plus bounded generation work; 5M D1 rows read, 1M writes, 1 GB storage; 100 monthly builds×8min. Within included paid allowances, proposed Cloudflare baseline ≈$5/month. Measure actual indexed rows/CPU rather than extrapolating record count. R2 standard pricing is $0.015/GB-month, $4.50/M class-A and $0.36/M class-B, with published free allowance and free egress; a <10 MB recovery ledger and thousands of operations are negligible but still metered. No export/artifact storage cost is assumed because those bodies are not retained in R2. [R2 prices](https://developers.cloudflare.com/r2/pricing/), [Builds allowance](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/).

At the documented model rate, 4,000 input + 1,600 output tokens costs $0.008+$0.0192=$0.0272/call. 1,000 calls ≈$27.20; add a conservative 5% uncertainty/spend reserve at $0.04 each ≈$2, so planning total ≈$34.20/month including Workers. Maximum admitted 1,000 calls at full $0.04 reservation is $40 generation; actual cap is $100/month independent of volume. No assumption of cache discount, batch discount or free evaluation credits. Optional frozen 720-call qualification at ≤$0.04/call reserves $28.80 plus pricing margin under $40; not run here. [Model pricing](https://developers.openai.com/api/docs/models/gpt-5.6-terra).

`Entitlements.generationAllowance` returns fixed free quotas in v1; no payment SDK, checkout, webhook table, subscription reconciliation or trial state. A later implementation returns an entitlement snapshot with reason/version/validity and authoritative subscription/invoice reconciliation behind that interface; policy changes still honor active quota reservations. Payment status never controls export, deletion or recovery. Legacy subscriber obligations are separate retirement inputs, not assumed to vanish because successor billing is disabled.

Public HTTP body limits are byte limits as well as schema character limits. Local development uses an explicit localhost origin/RP with synthetic data and no production secrets; production never accepts localhost, alternate origins or insecure transport. Missing recovery KEK/R2 blocks new security mutations and restore while established owned record access can continue when its session/data keys are valid.
